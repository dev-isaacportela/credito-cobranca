# Execução — estado do loop de construção

Arquivo de estado do loop autônomo. **Cada iteração começa lendo este arquivo e
termina atualizando-o.** Fonte de verdade do que está feito; não confie na memória
da conversa.

Pedido do usuário (14/11/2026): construir o **sistema inteiro** (7 módulos), em
loop, com o trabalho dividido entre agentes rodando em Opus 5.5 (Fable 5.2 até 14/11/2026), até entregar
o sistema completo rodando no simulador, com testes verdes.

## Regras do loop

1. Um agente por spec por vez; **dois agentes nunca escrevem o mesmo arquivo**.
   Arquivos compartilhados (registro de rotas, `PUBLISH_ORDER`, `package.json`,
   `setup-backend.mjs`) só são tocados pelo orquestrador ou pelas costuras
   por módulo descritas abaixo.
2. Costuras por módulo (criadas no esqueleto, fase 1), para o paralelo não colidir:
   - backend: `add-0N0-<slug>.mjs` (SFs e seed dos quadros; numeração em dezenas, ver arquitetura §8.3), `schema/NNN-<slug>.mjs` (DDL, importado
     pelo `setup-backend.mjs`), `simulator/seed/NNN-<slug>.mjs`,
     `simulator/smoke/NNN-<slug>.mjs`;
   - frontend: `src/modules/NNN-<slug>/` (telas, rotas e menu do módulo exportados
     por `index.ts`), `src/lib/<slug>/` (regra pura), `tests/NNN-<slug>.test.mjs`.
3. Nada de produção: nenhum `setup-backend.mjs`/`add-*.mjs` contra a plataforma,
   nenhum `VITE_MITRA_AUTH_URL` real, nada em `backend/migrations/`.
4. Pendências P-01..P-06 (`arquitetura.md` §6) **não bloqueiam**: seguem pelo
   padrão do artefato, parametrizado, e ficam listadas para o gestor.
   - P-01: padrão do código (protesto e bloqueio total em D+10), editável.
   - P-02: sem migração de dados nesta entrega.
   - P-03: Estética = mesmos padrões do privado, com parâmetro por segmento.
   - P-04: uma pessoa pode ser analista e agente; a segregação é por caso.
   - P-05: mapeamento do Winthor isolado num arquivo; colunas assumidas até a descoberta no sandbox.
   - P-06: modelos e encargos entram como "não validado" até o Jurídico validar.
5. Pronto de uma fase = `cd backend && npm test` e `cd frontend && npm test &&
   npm run build && npm run lint` verdes, e `tasks.md` da spec marcado.
6. Publicar na Mitra (Fluxo E) **não faz parte do loop**: o projeto ainda não
   existe na plataforma. A entrega termina no simulador + prompt do sandbox.

7. **Skills obrigatórias.** Todo agente que escopa, cria backend/simulador ou
   publica invoca `benenutri:mitra-escopo` (Skill tool) antes de começar e segue
   o fluxo correspondente (A escopar, B projeto novo, C feature, D rodar local).
   Todo agente que cria ou revisa tela invoca também `benenutri:design`
   (modo Instalar no esqueleto; Construir nas telas; Revisar na validação).
   Se a Skill tool não estiver disponível ao agente, ele lê o `SKILL.md` em
   `C:/Users/Isaac Portela/.claude/plugins/cache/benenutri/benenutri/0.10.0/skills/{mitra-escopo,design}/`.
8. **Agente validador.** Nenhuma fase fecha pelo relato de quem construiu. Ao
   fim de cada fase roda um validador independente (Opus 5.5, contexto novo, sem
   ver o relato do construtor), que **não corrige nada**: só lê, executa e relata.
   Ele confere:
   - spec ↔ código: todo C-00N e RN-00N tem `teste()`/`test()` cujo título começa
     com o id, e o assert prova o que a spec pede (não só "roda sem erro");
   - `cd backend && npm test`; `cd frontend && npm test && npm run build && npm run lint`;
   - `arquitetura.md` e `constitution.md`: tabela só do dono, prefixo `cc`,
     regra no servidor (alçada, segregação, visibilidade), política como
     parâmetro, auditoria em toda escrita, nada de CRUD REST em tela;
   - checklist "Antes de dizer que terminou" da `mitra-escopo`;
   - telas: anti-padrões do `design.md` §14 (modo Revisar da `benenutri:design`)
     e navegação real no simulador pelo navegador;
   - `tasks.md` marcado bate com o que existe.
   Saída: lista de achados com arquivo:linha, severidade (bloqueia / corrigir /
   observação) e como reproduzir. Achado que bloqueia volta para o construtor
   da fase (mesmo agente, via mensagem) e o validador roda de novo. A fase só
   fecha com zero bloqueios. Os relatórios ficam em `docs/validacao/NNN-<fase>.md`.

## Fases

Decisão do usuário (14/11/2026): **backend primeiro**. O frontend só é construído
depois que ele escolher, para **cada tela e cada aba**, uma entre **3 opções**
publicadas como artefato. As duas trilhas correm em paralelo e não tocam os
mesmos arquivos (backend em `backend/`; opções de tela em `docs/opcoes-tela/`).

tasks de backend marcadas. Tasks de frontend ficam abertas.
